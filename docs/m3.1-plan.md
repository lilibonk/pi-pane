## 1. 目标与完成定义

用户进入 `/web` 后，可以在网页中完成：**创建或打开主机项目目录 → 配置支持的模型账户或自定义供应商 → 选择主题 → 新建会话 → 执行任务 → 切换另一个项目 → 刷新后继续**。这条主流程不要求返回终端编辑配置或重新启动 pi。

M3 解决了交接、对话和工作台；M3.1 解决项目入口与原生配置的缺口。不能只用“页面有按钮”“保存了一个 JSON 字段”判定完成：项目必须真正影响运行时 cwd、资源和工具，账户必须应用到当前 RPC 运行时，设置必须明确作用域和何时生效。

对齐标准：对照 Kimi Code 网页时不照搬它的全部功能，只要求 **pi 与 Kimi 都有的同类功能在网页上保持一致，并使用 pi 自己的语义**；只有 Kimi 有的功能不算缺口。交集盘点见[调研索引](m3.1-research.md#对齐标准与取舍)。按此标准，本期在项目、账户、主题、设置之外，还须补齐自定义模型供应商和四项会话与结果功能；界面风格改版是维护者另行提出的并列缺口。

“原生配置补齐”采用完整盘点、逐项标注能力的方式，不承诺在这一期把任意终端 UI、每家供应商的所有认证方式、全部配置文件变成可编辑网页表单。首期可编辑清单在第 6 节；其余项目必须给出具体原因和下一步，不再笼统归因于“pi 不支持”。

### 不变约束

- `/web` 先结束 TUI，同一宿主进程在前台运行网页服务；不恢复镜像、`--web` 自启动、后台常驻、attach 或云中继。
- 同一宿主最多有一个已激活的 `pi --mode rpc` 会话写入者；宿主可管理项目记录、认证和明确许可的设置，但不写会话 JSONL 的内容；删除非当前且未被占用的已保存会话是用户明确发起的文件级操作，见 4.5。
- 回复、待发队列、扩展操作或对话框未结束时，不切换项目、不替换运行时。中止与清空队列必须由用户明确操作。
- 非预期 RPC 崩溃仍按 M3 停止服务，不自动重启。用户发起的项目/配置应用走独立、有限的受控替换流程。
- Ctrl+C 停止服务，打印最后实际项目/会话的终端恢复方式；终端关闭结束宿主及子进程。未落盘空会话提供回到该项目的命令，不能打印一个假称可恢复的文件。
- 外部访问沿用 M2 的 HTTPS 或同机代理、密码、二维码与令牌规则。现有认证控制端视为用户本人或其受信任设备，不新增访客、多租户或角色系统。
- 工具目录/启停和 tree 导航继续等待公开 RPC 支持；不新增私有扩展网关或凭 nonce 执行内部终端命令。
- 测试使用临时 HOME、agentDir、项目和确定性 provider。真实认证/模型试用需专用账户或本轮明确授权，不沿用已消耗的一次性凭据授权。

## 2. 已核实的事实与设计含义

| 问题 | 已核实事实 | 对计划的影响 |
|---|---|---|
| 新建项目是否被 pi 限死？ | 公开 SDK 可按 cwd 创建会话；标准 CLI 可在指定进程 cwd 启动 RPC。当前 pi-pane 仅把已有会话按 cwd 分组。[项目证据 P-E01–07、12–13](m3.1/projects.md#2-证据索引) | 增加独立项目管理与运行时切换；无需等待新上游命令才开始设计。 |
| 能否给 `new_session` 多传 cwd？ | pi 1.1.0 的命令没有该参数；`switch_session` 可恢复别的 cwd，但不改变进程级 `process.cwd()`。 | 同项目沿用原生 RPC；跨项目推荐顺序替换子进程，待 G1/G2 原型验证。 |
| 空项目等于已保存空会话吗？ | 会话有预分配路径，但首次 user/assistant 前可能没有 JSONL。 | 项目独立持久化；不伪造会话 header、不发送隐藏提示词。 |
| RPC 没有 login，网页就不能登录吗？ | 包根公开 `ModelRuntime.login/logout` 和 `AuthInteraction`；RPC 模型目录是运行时缓存。[认证依据](m3.1/auth.md#1-核心结论) | 宿主适配官方认证接口，成功后受控替换 RPC 应用；不能只写凭据再刷新下拉框。 |
| RPC 没有 theme，网页就不能换主题吗？ | `Theme`、`SettingsManager` 等是公开 API；RPC theme UI 是不支持的 stub。 | 主题由宿主/网页管理，区分浏览器外观与保存为 pi 默认。 |
| 设置写入成功如何判断？ | `setTheme` 写全局；项目可能覆盖。`flush()` resolve 不代表无错误，需检查 `drainErrors()` 及重新读取。 | 全局值、项目覆盖、有效值分别显示；不靠 toast 假报保存成功。 |
| 是否已证 Kimi 能创建磁盘目录？ | 本次实机证实添加启动目录之外的已有目录、空工作区刷新保留；未见 mkdir 入口。 | “新建目录”是本产品明确新增目标，不能写成已证的 Kimi 同款功能。 |
| `--approve` 能否只作用于一个项目？ | 已由 G2 原型证实：该覆盖对子进程内任何 cwd 的运行时都生效，且设置后不再触发全局扩展的 `project_trust` 事件；trustStore 的决定排在该事件之后；RPC 没有字段回报实际信任结果。 | 宿主不生成 `--approve`，首版不提供“仅本次信任”；子进程自行跨 cwd 切换不得被静默接受（4.3、4.4）。 |
| 子进程能否被交互式地正常停止？ | 已由 G2 原型证实并纠正：RPC 没有 shutdown 命令，宿主只能关闭 stdin。关闭阶段弹出的对话框无法回答，子进程不会挂起，而是立即以 0 退出并截断关闭处理；追加归属校验依赖存活子进程的 `get_entries`。 | 退出码 0 不代表关闭处理完整；stdin 关闭后出现对话框请求即判定停止不完整。关闭窗口内的追加只能有界接受，不能证明归属（第 8 节）。 |
| 凭据应用是否必须重启子进程？ | 已由 G3 原型证实不必：原生 `new_session`（未落盘）或对当前文件的 `switch_session`（已落盘）会重建模型运行时并读到新凭据，会话 ID、模型、历史不变。 | 选定进程内原生替换，换子进程只作回退（5.2）。 |
| 启动参数里的模型会不会覆盖会话选择？ | 已由 G2 原型证实：以 `--model` 恢复会话时启动参数覆盖会话里保存的模型，不带时恢复会话的模型。 | 重建同一会话时不重放这两类参数（4.3）。 |
| 网页输入的密钥会不会被当作命令？ | 已由 G3 原型证实会：以 `!` 开头的原始字符串交给官方登录后被当作宿主命令执行；按 pi 的转义规则处理后解析回原文。 | 所有网页输入的密钥必须先转义为字面值（5.3、5.4）。 |

基线固定：pi / pi-ai **1.1.0**，上游提交 `abe508e1b89912adde45528136c3221eb69acdd7`；Kimi Code **2.1.1**，上游提交 `242ac230006447f8601e1678c49182bfbae89fe9`；pi-pane `c2c39e6f7a84c7e8490bbca587528cb195524e22`。不以最新 main 的接口替代这次基线。

## 4. 项目管理设计（P0）

### 4.1 用户入口与数据

侧栏先显示项目，再显示该项目会话。提供“打开项目”“新建项目”“最近项目”“从列表移除”；空项目显示“尚无会话”，当前项目始终可辨认。新建会话按钮明确归属当前项目。移动端用抽屉承载同一入口，项目选择完成后回到对话区。

项目是主机上的目录。打开入口使用主机目录选择器：当前位置、父级、子目录列表、直接输入绝对路径；初始入口为当前目录、最近目录和主目录，不后台递归扫描磁盘。手机访问时明确显示“选择运行 pi 的电脑上的文件夹”，不用浏览器文件上传或本机目录 API 代替服务器路径。

首版使用 M2 既有 owner 信任边界，不新增目录沙箱；仍受主机 OS 权限约束。目录选择器只列目录及必要状态，不返回文件内容或读取凭据。

项目根可选之后，既有 `WorkspaceService` 的敏感过滤不再自动成立：它按“相对项目根的路径”判断排除项，根目录本身位于 `.ssh`、`.aws` 或 agentDir 之内时，过滤对其下文件失效。因此新增一条明确的根目录限制：项目根 realpath 的任一路径段属于凭据类目录（`.ssh`、`.gnupg`、`.aws`、`.azure`、`.pi`、`.codex`），或位于有效 agentDir、会话目录、pi-pane 数据目录之内时，网页拒绝把它打开或创建为项目，并提示在终端进入；“重新定位”使用同一判断。`build`、`dist` 等仅为降噪而排除的目录名不在此列。`WorkspaceService` 的相对路径过滤保持不变。

建议项目注册表：`<有效 agentDir>/pi-pane/projects.json`。版本化 schema，保存 `projectId`、canonicalPath、显示名、创建/最近打开时间、最后已保存会话引用和来源；不保存聊天、key 或访问 token。realpath 去重；项目注册和现有会话目录合并呈现；仅因历史会话发现的项目可不立即写盘。并发宿主用锁、读改写和原子替换，损坏时保留原文件并提示，不静默清空。

“从列表移除”只移除/隐藏入口，保留目录与会话；历史发现不能在刷新后立即把被移除项重新加回来，需记录隐藏选择。当前项目先切走再移除。目录缺失或移动显示不可用，重新定位必须用户选择；不能自动切到同名目录。

### 4.2 打开与创建流程

打开：选择路径 → realpath/目录/权限检查 → 列出现有会话或准备空会话 → 处理项目信任 → 检查当前运行时可离开 → 执行切换 → 新快照确认 → 更新当前项目及最近记录。目标项目的最后已保存会话引用仍然有效时恢复该会话，否则进入新的空会话；用户可在侧栏改选。会话目录中 cwd 与当前项目不同的会话由宿主改走本流程，不再直接发原生 `switch_session`。

创建：选择现存父目录 → 输入单段目录名 → 显示最终路径 → 排他 mkdir → 注册项目 → 执行打开流程。允许中文、空格和合法标点；拒绝空名、`.`、`..`、分隔符和 NUL。全部走文件 API，不能拼 shell。父目录对象在确认与创建之间发生变化时重新校验。同名已有目录提示“打开已有项目”；重发命令按命令 ID 返回原结果，不再次 mkdir。

后续启动失败时保留已创建的空目录和项目入口，并显示失败原因；不自动递归删除可能已有用户文件的目录。仅取消未执行的创建表单不改磁盘。

### 4.3 信任与启动参数

公开 `ProjectTrustStore` 可读写信任决定；RPC 没有 TUI 信任提示。网页必须让未知且含需信任资源的项目选择：信任并记住此目录、不加载继续、取消；首版不提供信任整个父目录。

首版不提供“仅本次信任”。pi 唯一的一次性手段是 `--approve`，而它对该子进程内任何 cwd 都生效，并跳过全局扩展的 `project_trust` 事件，无法兑现“只对这个项目、不绕过全局政策”。因此宿主从不自行生成 `--approve`：“信任并记住”写入 `ProjectTrustStore`，由子进程按原生顺序（全局扩展事件 → store → 默认策略）解析；“不加载继续”使用 `--no-approve`，它同样是进程级，但方向是少加载，只在本次打开该项目期间有效，离开后再次打开重新询问。

信任允许加载项目配置、扩展和声明的包，**不等于工具文件系统沙箱**；不信任也不意味着 AGENTS 上下文完全忽略。全局 `project_trust` 扩展可以否决已写入的信任记录，且 RPC 不回报实际信任结果，所以界面把“用户的选择”和“实际加载情况”分开显示：后者以新快照中的命令和资源来源为依据，无法确认时显示未知，不显示“已信任并加载”。

用户启动 pi 时自带的 `--approve`/`--no-approve` 只在子进程启动于起始项目时重放，不带到其他项目。它仍是进程级覆盖，所以带着它运行的子进程一旦自行切到别的 cwd，按 4.4 的规则失败关闭。

增加有类型的 `LaunchProfile`，逐项记录来源和范围：

| 参数/配置 | 跨项目行为 |
|---|---|
| 显式进程级 provider/model/thinking/tools/no-* | 新会话与新项目保留用户明确的启动覆盖，并在设置面板显示覆盖来源；用户当前会话的临时选择不冒充另一项目默认。重建**同一会话**（凭据/设置应用、失败恢复）时不重放 provider/model/thinking，由会话记录恢复；重建后核对与停止前一致，不一致则提示并等用户确认，不静默换模型。`/web` 交接本身同样处理：会话已落盘时不重放启动模型，与交接前不同则在终端和页面提示 |
| 显式 extension/skill/template/theme 路径 | 相对路径在原启动目录解析并固定；新项目自动发现资源重新加载，不能将相对路径偷偷重新解释 |
| `--approve` / `--no-approve` | 用户原始参数只绑定起始项目；宿主只会为“不加载继续”生成 `--no-approve`，从不生成 `--approve` |
| `--session`、resume/continue/fork、初始提示/@文件 | 由目标操作重新生成；初始提示和文件不重放 |
| sessionDir | 区分显式 CLI/环境覆盖、目标项目设置、默认目录；不能将旧项目目录当全局默认 |
| 扩展 flags、system prompt 文件/文本 | 保留已解析且有明确语义的值；目标不支持时给出错误，不吞参、不猜测文本是路径 |
| 环境变量 | 子进程始终继承宿主起始 shell 的环境，不模拟 direnv、虚拟环境或 shell hook；agentDir、会话目录等 pi 环境变量按全进程显式覆盖处理。项目面板标明“环境来自启动 `/web` 的终端”，迁移文档说明它与 `cd <项目> && pi` 不等价；本期不提供环境编辑 |

### 4.4 当前会话与跨项目切换

同项目新建、恢复、分叉继续标准 RPC，保留原生扩展取消语义。跨项目统一推荐 **停止旧 child 后在目标 cwd 启动新 child**，使 `ctx.cwd`、内置工具和 `process.cwd()` 一致，避免项目扩展读取旧进程目录。

此方案的兼容边界必须公开：标准 RPC 没有只询问旧扩展 `session_before_switch` veto 的 preflight；跨 child 替换按结束运行时处理，不能承诺与同进程原生切换完全等价，也不能保存任意扩展内存。G2 必须验证正常 shutdown 和可接受的用户语义；如维护者要求所有扩展 veto 完整保留，本路线存在实质缺口，先作架构决策，不加私有网关绕过。

“当前项目 = 子进程启动 cwd = 会话 cwd”是宿主必须维持的不变量。扩展命令可以通过公开命令上下文让子进程自行切到另一个 cwd 的会话，此时 `process.cwd()` 仍是旧项目，信任按无 UI 规则或进程级覆盖解析，目标项目的资源已经加载。宿主在每次写操作后的状态核对中发现会话 cwd 与当前项目不一致时，不得静默接受：默认失败关闭（停止服务并打印恢复命令）。G2 可评估改为受控重建到该项目，但带信任覆盖启动的子进程只能失败关闭。

空会话采用候选 A（G1 已验证并选定）：不传 `--session`，标准 CLI 在目标 cwd 自行创建会话并按原生规则决定 sessionDir，包括项目设置的 sessionDir；宿主在 `get_state` 返回预分配路径后、第一条消息之前取 sidecar 锁，与 M3 `session_new` 的现有顺序相同。G1 证实加锁前以及切换模型、命名、执行命令之后都没有文件落盘。宿主预分配路径的候选 B 已放弃：现有锁在会话目录不存在时失败，子进程的 sessionId 与预分配文件名不一致，且后续新会话的目录与项目设置分叉。宿主不写 JSONL，以子进程实际 `sessionId` 为准；路径存在与会话已落盘是两个状态。

项目列表保留空项目；跨项目离开未落盘空会话后，保证恢复项目和网页草稿，不承诺恢复该 child 的临时扩展内存。草稿、图片/附件引用按 projectId + session/draft 身份隔离；旧目录同名文件不能自动解释为新目录文件。

### 4.5 会话与结果补齐（P2）

这四项是 pi 与 Kimi 都有的同类功能，0.2.0 网页没有或标为“终端专用”。

- **删除会话**：对应 pi 会话选择器里的删除。RPC 没有删除命令，由宿主执行。只能删除会话目录中已暴露 ID 的已保存会话；当前会话、被任一 `/web` 宿主持锁的会话拒绝删除。删除前二次确认并显示名称、项目和路径。与 pi 相同，优先移入系统废纸篓（以参数数组调用 `trash`，不经 shell），不可用时才永久删除，界面如实说明是哪一种。普通 TUI 不持锁，宿主无法探知它是否正打开该会话，确认框须提示。删除后刷新目录，并清理项目注册表里指向它的最后已保存会话引用。
- **导出会话**：对应 `/export`。HTML 用标准 RPC `export_html`。G5 证实不带路径时文件会落在子进程的工作目录即用户项目里，所以宿主**始终传入自己指定的输出路径**（位于 pi-pane 数据目录下的导出目录），结果显示该路径；另经已认证 WS 的定向分块提供浏览器下载，有大小上限，超限只给路径。浏览器不能指定任意宿主输出路径。JSONL 导出没有 RPC 命令，本期只交付 HTML 并注明。导出内容可能含凭据与文件内容，导出前提示。
- **复制回复**：对应 `/copy`。用标准 RPC `get_last_assistant_text` 加浏览器剪贴板，每条助手消息另有复制入口；剪贴板不可用时退为可选中文本，不报成功。
- **会话信息与用量**：对应 `/session`。用标准 RPC `get_session_stats` 显示会话文件、ID、消息与工具调用数、token、费用和上下文占用；输入区常驻上下文占用指示。`/session` 不再跳到资源页。

## 5. 账户与认证设计（P1）

### 5.1 支持范围与状态

设置中的“账户与模型”显示 provider、可用认证方式、已保存/环境配置等来源、最近操作结果和可用模型入口。pi 的账户以有效 agentDir 全局共享，不画成每项目独立账户，也不编造邮箱、额度、组织或订阅信息。

第一批开放普通 API key provider：OpenAI、Anthropic、Google Gemini、Qwen Token Plan Individual；OAuth 以设备码（device code）流程为必交类型：pi 1.1.0 内置的设备码登录有 `kimi-coding`（pi `/login` 中显示为“Kimi Code (subscription)”）、GitHub Copilot、xAI 等，实现对这一类型通用，不为某一家写专门代码；真实试用选维护者授权的那一家。这里的 `kimi-coding` 是 pi 自带的模型 provider，与本计划把 Kimi Code 网页当作界面参照是两件无关的事，pi-pane 不接入 Kimi 产品自身的账户体系。OpenAI Codex 和 Anthropic OAuth 在完成相应 callback/manual/device 用例及真实授权试用后可加入支持矩阵，否则明确未验证并禁用该网页登录方式，已有凭据仍可用于会话。OpenAI provider 的 ChatGPT OAuth 与 `openai-codex` 分开；其他设备流、企业域名、AWS/Vertex ambient 认证逐项扩充。

至少一个 API key provider 和一个 pi 内置设备码 provider 完成经授权的真实闭环，才可声称网页认证目标完成；未拿到账户授权时记录验收待办，不伪称确定性模拟等同真实登录。各 provider 的具体边界见[认证支持表](m3.1/auth.md#3-provider-首批范围建议)。

Kimi 的“新增服务商、协议、Base URL、模型 ID/上下文”与 pi 的 `models.json` 兼容端点配置是同类功能，本期按 5.4 交付。它与内置 provider 的登录是两件事，不能把 login 按钮称为已完成自定义供应商对齐。

状态至少区分：未配置、配置可用但未作远端验证、授权进行中、凭据已保存待应用、已应用、失败/已取消。API key 接受并保存不等于远端验证成功；清除保存凭据不等于撤销供应商授权，也不等于清除 shell 环境或 CLI key。

### 5.2 宿主适配与凭据应用

只使用当前 pi 安装的公开 `ModelRuntime` 和 `AuthInteraction`；不创建第二个 AgentSession，不为了列认证方式完整加载项目扩展。内置 provider 用不自动解析项目模型配置的认证运行时；自定义/扩展认证暂不另行加载到宿主。

流程分两段。**认证交互**：取得账户操作互斥 → provider 选择 → 按公开接口渲染 secret/text/select/manual_code、auth_url/device_code/progress → 官方实现交换和保存 credential → 标记“已保存待应用”。**应用**：确认运行时空闲 → 让 RPC 运行时重新读取凭据 → 获取新模型目录和当前状态 → 显示已应用。

应用方式选定**进程内应用**（G3 已验证）：未落盘空会话发原生 `new_session`，已落盘会话对当前文件发原生 `switch_session`。两者都会重建模型运行时并读到新凭据，会话 ID、当前模型和历史不变；它保留扩展的 `session_before_switch` 取消语义，不换锁、不关 stdin，扩展在替换过程中的对话框仍可应答。扩展否决时旧运行时继续可用，状态保持“已保存待应用”。**换子进程**只作回退，走第 8 节流程，G3 证实它同样生效。无论哪种，应用只作用于本宿主的运行时；同一 agentDir 下其他 `/web` 宿主或 TUI 不会被刷新，界面与文档须说明。

认证交互不占用会话。设备码授权可能持续十几分钟，用户还可能离开页面，因此交互期间对话、会话和项目操作照常进行；账户操作互斥只排斥另一次账户操作和其他全局配置写入。空闲门槛只加在“应用”这一步：凭据保存时运行时空闲就立即应用；否则保持“已保存待应用”，由用户在空闲后触发，不在回复结束时自动替换运行时。应用开始后按运行时替换事务对待，期间新的 prompt、命令、模型/会话/项目切换返回 busy，并清点已分派操作，不与进行中的扩展请求重叠。

认证数据只进入实际 agentDir 的官方 AuthStorage。浏览器不可提交任意 authPath。沿用官方文件锁和 provider 修改队列；不复制日常凭据到 pi-pane 自己的配置。`CredentialSynchronizationError` 可携带 credential，只投影有限错误码；凭据已保存而同步失败时保留真实状态，提供“重新应用”，不重复登录也不擅自回滚凭据。

同一会话恢复时优先保留原模型和 thinking；被清除的账户导致原模型不可用时提示重新选择，不能静默换供应商并发送。环境/CLI 覆盖仍生效时显示来源及限制。模型失败属于实际结果，不因本地 credential 存在而隐藏。

### 5.3 交互保密、取消与远程

认证交互单独绑定发起浏览器的 lease 和 operation/step，其他页面只看到“账户配置进行中”。任何已认证页面都可以取消该操作（同属 owner 边界），但只有发起 lease 能看到和回答步骤。不复用现有广播式扩展对话框；不将 key、code、OAuth state、完整回调 URL 放入聊天、草稿、本地存储、通用 receipt、快照、日志或测试截图。命令去重仅保存无秘密的操作标识和结果；secret 提交保存在处理中的内存，提交后清空输入。

当前 step 只接受一次有效答案；旧 step、跨 lease、跨操作回答拒绝。刷新可通过原 lease恢复未提交步骤，但不回显已提交 secret。

操作的存续不绑定 WebSocket 是否在线。手机用户必须离开页面去授权，后台标签页的连接会被系统挂起；按断线计时取消会让移动端 device flow 无法完成。取消条件为：任一已认证页面显式取消、provider 流程自身到期（如设备码有效期）、操作绝对上限（建议 15 分钟，G3 校准）、发起 lease 失效或访问凭据撤销、宿主退出。任一条件满足即释放授权轮询和 callback 端口。发起页重连后看到当前步骤或最终结果；发起 lease 已失效时，已保存的凭据仍如实显示为“已保存待应用”，任何页面可触发应用。

手机号/远程浏览器不能把自己的 localhost 当作 pi 主机。优先官方 device flow 或手动回填；不把 provider 的 localhost callback 监听暴露公网。provider 没有合适路径时说明限制，不能自造 OAuth 交换协议。

API key 字段是字面密钥，不是命令或变量表达式编辑器。pi 把保存的密钥当作配置值解析：开头的 `!` 表示执行命令，`$NAME` 表示环境插值。G3 证实未经处理的 `!` 开头输入会在宿主上被执行，因此宿主把网页输入交给官方登录之前**必须**按 pi 的转义规则处理（`$` 写成 `$$`，开头的 `!` 写成 `$!`）；G3 用 8 种输入证实处理后解析回原文且没有命令被执行。这是硬性要求。只读账户列表不得为显示状态而执行已有 key command。

### 5.4 自定义模型供应商（P1）

pi 的同类能力是在有效 agentDir 的 `models.json` 里配置接入已支持 API 协议的端点。pi 没有对应的交互入口，也没有公开的写入接口，所以网页提供结构化表单并由宿主写文件；它不是 JSON 编辑器。

- **字段**：供应商名称、API 协议（从当前 pi 版本支持的协议中选择）、Base URL、API key、模型列表（模型 ID 必填，上下文长度与显示名可选）。表单未覆盖的字段（headers、`modelOverrides`、`inputLimits`、采样参数等）原样保留并只读显示，不因保存而丢失。
- **写入**：宿主对 `models.json` 做加锁的读改写和原子替换，只改动目标 provider 条目。文件无法解析时拒绝写入并保留原文件；每次提交带期望版本，外部改动后拒绝并刷新。表单拒绝与内置或扩展 provider 同名：G5 证实同名条目的实际语义是把模型并入内置列表并改写该 provider 的端点，不是新增供应商。
- **密钥**：`models.json` 的 `apiKey` 支持字面值、`$NAME` 环境插值和 `!command`。G5 证实 `models.json` 的条目可以不含密钥，密钥经官方登录存入凭据文件后模型即可用，所以网页保存的密钥**只存入官方凭据文件**，不写进 `models.json`，并与 5.3 一样先转义为字面值。已有的命令型或环境型配置只显示类型，不执行、不回显。密钥保存后不回显，只显示“已设置”。
- **Base URL**：只接受 http/https，非回环的明文 http 给出警告。保存不发起连通性探测，状态显示“已配置未验证”，首次模型请求的结果如实显示。
- **应用**：与凭据应用共用 5.2 的方式和空闲门槛，保存与应用是两个结果。G5 观察到运行中的子进程下一次列模型时就会看到文件改动，但界面状态仍以应用结果为准。删除供应商前显示受影响的模型数；当前会话正在使用其模型时提示重新选择，不静默换模型。

## 6. 主题与设置设计（P1/P2）

### 6.1 三层作用域

1. **此浏览器**：外观、字号、是否折叠 thinking 等纯显示偏好；本地持久化，不修改 pi 配置，不广播强制改变其他设备。偏好按网页 origin 保存；本地模式未指定端口时端口可能在 7878–7897 间变化，origin 随之改变，偏好与草稿不跨端口保留，界面和文档须说明，需要稳定保留时使用固定端口。
2. **当前会话/运行时**：模型、thinking、队列策略、自动压缩等有标准 RPC 的操作；明确是否由上游同时保存默认值，不能在 UI 假称“仅本次”却写全局。
3. **pi 全局默认**：通过公开 SettingsManager 的明确 setter 写有效 agentDir 设置。当前项目值和 CLI 覆盖单列展示；有覆盖则说明新默认对当前项目未生效。首版不提供任意项目 settings 写入，也不假设存在通用 `setProjectSettings`。

所有设置项携带名称、当前有效值、全局值、项目覆盖/CLI来源、可编辑性原因、保存位置与生效时机。无法从公开接口可靠确认的来源显示“未知”，不推断一个确定来源。

### 6.2 主题

提供网页外观“跟随 pi / 跟随浏览器系统 / 浅色 / 深色 / 指定 pi 主题”和立即预览；预览取消恢复原外观，“清除此浏览器偏好”回到跟随pi。首次沿用交接时已解析主题，已有浏览器偏好优先级显式定义为：该浏览器明确选择 > 当前项目有效 pi 主题 > 交接快照回退。

pi `system` 是终端调色板，网页“跟随系统”是浏览器媒体偏好，二者不能共用含糊的标签。未能在无 TUI 的新项目中解析 terminal system 时使用交接快照，并提示来源；用户可选网页系统外观。自定义主题读取失败/名称冲突/缺失时保留最后有效颜色并显示问题，不出现白屏。

主题目录只包含通过公开资源信息可发现并安全解析的已安装主题；继承交接时 theme 清单，跨项目重建目录。包根未导出的内部 loader 不能 deep import。仅为列主题不得完整 reload 项目扩展；若公共入口无法单独解析，G4 选择已验证 JSON 适配与公开 Theme构造，或明确暂不支持该来源。

“保存为 pi 默认主题”是另一个明确动作，用全局 `setTheme`；显示受影响 agentDir 和项目覆盖。保存后验证磁盘及有效值，网页当前外观仍按该浏览器选择显示。未来新开的 TUI应读取所保存默认；不承诺修改另一个正在运行的 TUI。

纹样类装饰属于主题层，但不在 pi 的主题格式之内，只随 pi-pane 自带主题提供，机制见第 7 节“主题装饰”。把带装饰的主题保存为 pi 默认时，只保存主题名，TUI 只得到配色。

### 6.3 首批可编辑设置

下表为拟交付 allowlist；每个 setter、RPC 是否还写默认值必须经 G4 核验后在界面标明。没有明确作用域/错误反馈的项不直接上线。完整原生字段盘点与暂缓理由见[设置附录](m3.1/settings.md)。

| 设置 | 拟定入口/优先级 | 作用域与生效时机 |
|---|---|---|
| 主题与网页显示偏好 | 外观 / P1 | 浏览器即时；另选保存 pi 全局默认 |
| 当前 model/thinking | 账户与模型 / 已有能力整合 | 标准 RPC，仅当前会话；默认值保存是另一个操作；旧会话恢复优先级明确 |
| defaultProvider/defaultModel/defaultThinkingLevel | 模型默认 / P2 | 全局默认；以后创建的运行时/会话，项目/CLI覆盖可见；不覆盖已保存会话选择 |
| steeringMode/followUpMode | 会话行为 / P2 | 标准 RPC；空闲应用。G4 证实它同时写入全局默认，界面须标明 |
| compaction.enabled | 会话行为 / P2 | 标准 RPC；G4 证实它同时写入全局默认，界面须标明 |
| retry.enabled | 会话行为 / P2 | 标准 RPC与配置回读，G4 证实它同时写入全局默认；get_state无此字段，实际效果通过确定性临时失败验证，项目覆盖仍可生效 |
| images.blockImages | 会话行为 / P2 | 全局默认；G4 证实它对经 RPC 发送的图片生效 |
| hideThinkingBlock | 外观 / P2 | 网页显示开关；若另存 pi 默认，明确两层效果，原始会话不删内容 |

本期只读：项目覆盖、sessionDir、内置与扩展 provider/model 的来源、资源列表（自定义供应商按 5.4 可编辑）。终端专用字段注明对网页无效。高级compaction数值、agent/provider重试数值、`enabledModels`/每模型budgets和覆盖、cache warming、默认工具/codemode、资源安装/MCP、任意shell设置等先保留只读及具体原因；不因有 setter 就无范围地开放。其中 `enabledModels`（对应 `/scoped-models`）、资源包安装与启停（对应 `pi install`、`pi config`）、MCP 管理（对应 `/mcp`）是 pi 与 Kimi 都有的同类功能，按对齐标准属于待补齐项：本期只读并写明原因，列入 M3.1 之后的首批工作。

`images.autoResize` 未经验证，保持只读并显示当前网页图片限制，不能声称完整继承。主题全局默认须保留固定主题与light/dark配对表达，不能用只返回单一名字的getter丢掉自动配置。

### 6.4 保存、冲突与应用

`SettingsManager` 使用公开存储后端和 setter，保留未知/扩展字段；禁止将网页拿到的整份旧 JSON 覆盖回磁盘。创建manager时显式传当前cwd、有效agentDir和实际projectTrusted，不能利用其默认trusted值跳过项目信任。会话写串行队列与宿主管理操作统一协调，但设置保存本身不获得写会话文件权限。响应只包含允许展示的字段，不返回含扩展私有数据、代理凭据或设备标识的原始settings对象。

每次提交带 settingKey、期望旧值/版本和新值，服务端验证 allowlist/类型/范围；同一宿主 stale 直接拒绝并刷新。对其他 pi 进程，遵循官方文件锁和读改写行为；能够合并不同字段不等于公开 API 提供严格 CAS。G4 必须定义同字段竞争语义：默认接受官方串行的后写生效并重新读取提示，不能宣称完全防止外部覆盖。

保存成功必须同时满足 flush、drainErrors 无失败、重新读取目标字段及有效值确认。若磁盘写失败而内存值已改变，重新建立设置视图并恢复显示，不能通过用旧整文件回写实现“回滚”。保存成功但 child应用失败时保留“已保存、待应用”，使用同一运行时恢复流程。需要重建运行时才生效的设置与凭据应用共用 5.2 的两个候选，优先进程内应用。

上述flush/errors检查针对宿主自己的SettingsManager。RPC设置没有远程flush/read-errors命令，必须另做验证：队列和autoCompaction用get_state加磁盘回读；retry无直接运行态字段，以命令结果和有效配置确认保存，测试用确定性临时失败验证实际重试行为，界面标明确认依据。保存回读超时显示“运行态操作已接受，保存状态未确认”，不能假报成功或因此杀会话。队列setter直接改变agent状态，compaction/retry则读取合并后的有效配置，遇项目覆盖时不能使用一套假定全部即时生效的保存逻辑。

## 7. 页面、slash 与协议

### 页面结构

侧栏：项目列表、当前项目会话、搜索、新建/打开项目；会话行内操作增加删除与导出。设置：账户与模型（含自定义供应商）、外观、会话行为、项目与配置来源、资源/兼容性。右侧文件/Git 保持现有定位。助手消息增加复制入口，输入区显示上下文占用，会话信息有独立入口。首次无账户时给登录入口，空项目给新建会话入口，错误状态给可以实际执行的恢复动作。

`/login`、`/logout`、`/settings`、`/model`、`/new`、`/resume`、`/session`、`/export`、`/copy` 等原生保留名由网页拦截并打开对应入口。主题通过设置选择；若提供 `/theme`，明确是 pi-pane 入口而非声称 pi 原生命令。未知扩展/skill/模板遵循现有 RPC 展开。tree/工具管理未支持时显示原因，绝不把内置交互命令原文发给模型。

### 界面风格

当前网页的设计风格需要改，这是维护者明确提出的缺口，与功能缺口并列。0.2.0 的界面是固定深色、描边密集、控件堆叠的工具面板：顶部品牌栏独占一行，侧栏把新建、重命名、克隆、搜索和标签页逐个堆成按钮，设置与资源挤在右侧面板的标签里，输入区上下常驻说明文字。Kimi 2.1.1 网页是留白较多的工作台：侧栏是导航列表，空状态以居中输入框和项目选择器为主，设置是带分类导航的独立弹窗，边框弱、圆角大。逐项对照见[调研索引](m3.1-research.md#界面风格缺口)。

方向（维护者 2026-10-10 确认）分三层，各层互不越界：

| 层 | 管什么 | 来源 |
|---|---|---|
| 结构 | 侧栏、空状态、设置、供应商表单等同类页面的信息架构与入口位置 | 以 Kimi 2.1.1 网页为参照 |
| 视觉语言 | 字体与字号阶梯、间距、圆角、边框、阴影、密度、组件状态、动效 | pi-pane 自己的设计，不照抄 Kimi 的观感 |
| 主题 | 颜色，以及纹样等可整体更换的装饰 | pi 主题，用户可换 |

为了不与主题功能重叠，设计受以下约束：

- 设计规范只规定“哪里用哪个颜色角色”，不写死颜色值，任何 pi 主题下都必须成立。品牌色渐变、固定彩色描边这类依赖具体色相的做法不采用。
- pi 主题原为终端设计，只有颜色。网页需要而主题没有的角色（浮层、悬停、阴影、焦点环）从现有主题颜色推导，不另起一套调色板。
- 颜色上的辨识度通过重做 pi-pane 自带的 `pi-pane-light`、`pi-pane-dark` 两个默认主题来表达。它们是主题，用户换用其他 pi 主题时让位。
- 纹样类装饰（例如青花瓷纹样）属于主题层，不属于视觉语言：它与配色成套，可以整体更换。设计规范只预留装饰位并规定边界；装饰内容由主题提供，加载机制见下文“主题装饰”。

交付内容：

- 关键页面稿的评审记录。
- 一套设计规范：颜色角色表、字体与字号阶梯、间距、圆角与边框、装饰位，以及按钮、输入、列表、弹窗、提示等组件的各种状态。
- 重做后的 `pi-pane-light`、`pi-pane-dark` 两个默认主题。
- 主题装饰的加载机制，以及随包发布的青花瓷主题 `pi-pane-porcelain`（配色加纹样）。
- 现有工作台与本期新增的项目、账户、供应商、设置页面全部按规范实现，不留新旧两套风格并存；桌面与 390px 移动端一致。

改版不改变协议与功能语义，不降低既有的键盘可达、焦点可见和对比度要求；ThemeMapper 的语义 token 通路保留，pi 主题仍能驱动配色。为避免返工，设计规范先于 M31-2 至 M31-4 的页面实现完成。

### 主题装饰

装饰是 pi-pane 对主题的扩展。pi 的主题格式只有颜色，主题文件还会被 TUI 加载，所以不往主题 JSON 里加字段，而是用随包发布的独立清单把装饰绑定到自带主题上。

- **清单**：每个带装饰的自带主题对应一份装饰清单，放在主题目录之外的独立顶层目录，不会被 pi 当作主题加载。清单是固定结构的数据：装饰位 → 素材标识、着色用的主题颜色角色、不透明度上限、平铺方式。不含 URL、路径或 CSS 文本。
- **素材**：单色 SVG，随包发布，由 Hub 的静态资源通路同源提供，有总大小上限。素材以遮罩方式着色，颜色取自清单指定的主题颜色角色，素材本身不带颜色。
- **绑定**：装饰只绑定到来源路径位于本包主题目录内的主题，不按名称匹配；第三方主题即使同名也不会获得装饰。清单与素材在构建时和加载时各校验一次，校验失败则不显示装饰，页面其余部分不受影响。
- **装饰位**：由设计规范定义，限于品牌区、空状态背景、设置弹窗页眉、分隔处等不承载内容的区域；不出现在正文、代码、diff、表单和工具输出之下。没有装饰时布局不变。
- **开关**：外观设置提供“显示主题装饰”，属于此浏览器的偏好，默认开启。系统请求高对比度或强制颜色时自动不显示；窄屏按规范缩减或隐藏。
- **协议**：主题查询只返回该主题的装饰清单标识与已校验的装饰位数据，不返回宿主路径。

青花瓷主题 `pi-pane-porcelain` 是随包发布的浅色主题，由两部分组成：一份完整的 pi 主题（56 个颜色齐全，白地青花配色），和一份装饰清单加纹样素材。它在 TUI 中只表现为配色，在网页中另带纹样；选用其他主题时纹样随之消失。本期只提供浅色一套，不承诺对应的深色版本。纹样素材须为原创绘制或来源与授权清晰，并在仓库中记录来源；不使用来源不明的图案。

### 协议草案（均为拟新增，不是现有 API）

- 读取继续唯一 `workbench_query`：增加 projects、project_directories、accounts、providers、themes、settings、session_stats 等有类型 action；回复定向、有大小限制。宿主级查询不依赖某个活着的 session，需对现有 session-scoped校验作显式版本扩展。
- 变更继续普通 command/ack/result 和序号去重：project_create/open/remove、account_begin/cancel/logout/apply、provider_save/remove、theme/settings_apply、session_delete、session_export 等；客户端不能直传任意 RPC、文件写路径或 shell。
- session epoch/revision 保护会话动作；host configuration revision保护项目/全局配置；operationId + stepId + ownerLease绑定认证交互。三者目的不同，不能拿旧 session epoch无限阻止恢复页读取宿主状态。
- 已实现的最小形态（M31-1）：宿主状态 `host_state {revision, phase, cwd, recovery?}` 在握手后先于快照下发并在变化时广播，不含会话文件路径；恢复操作用 `host_command {clientId, commandNo, id, hostRevision, command}`，命令为 `recover_retry`、`recover_restore`、`host_stop`，与普通命令共用同一租约的编号和回执去重，按 `hostRevision` 校验。后续的项目、账户、设置命令沿用这一信封。
- 宿主级恢复快照及管理命令也不能依赖活着的child/Bridge：account_apply/cancel、重试目标、恢复旧项目、停止服务按host revision及operation/owner校验。启动失败后刷新页面或新页面重连仍能看见恢复入口；认证操作依旧只有原owner能续答，取消则对任何已认证页面开放。
- secret回答使用同一受认证 WS 的定向控制消息和专门安全 DTO；不走会保存完整参数的通用调试/receipt路径。不新增 HTTP 读取后门或扩展私有通道。
- child成功替换后发布新 session epoch和完整 snapshot，随后刷新命令、模型、主题、文件/Git。旧请求不跨代继续，只有触发该事务的普通回执保留原命令关联。
- 对旧网页协议版本做握手兼容判断和“请刷新”提示。协议是否升主版本由最终字段兼容性决定，不能既更改必填字段又继续假称兼容。
- 宿主启动及每次运行时换代时探测所依赖的公开导出（`ModelRuntime` 的认证方法、`ProjectTrustStore`、`SettingsManager` 的相关 setter、RPC 入口）。缺失或签名不符时对应功能显示为不可用并给出 pi 版本原因，不崩溃、不 deep import；peer 范围 `>=1.1.0 <2` 不等于这些接口在范围内都稳定。

## 8. 受控运行时替换与故障处理

```text
ready → validating → awaiting_trust → preparing_target
  → stopping_old → starting_target → verifying_snapshot → ready
                         失败 → recovery_required
recovery_required → 用户重试目标 / 恢复上一个已保存会话 / 停止服务
任何阶段收到 Ctrl+C / SIGHUP → stopping → stopped
已就绪活跃 generation非计划退出 / 会话外部冲突 → M3 fail-closed 停服务
本次替换事务内候选child在readiness前启动失败 → recovery_required
```

1. 前置检查不破坏旧运行时；目标路径、配置、信任、可获得的目标锁先验证。busy/旧版本/锁争用返回具体原因。
2. 保存旧 descriptor：实际 cwd、sessionFile、是否落盘、CLI来源、模型/thinking、已批准目标；草稿在浏览器独立保存。
3. 预留目标锁（空会话没有可预留的路径，改为启动后加锁，见 4.4）。趁旧 child 仍存活完成最后一次追加归属校验和空闲复核，记录基线，然后发起计划停止并等待它真正退出；此后才能激活目标 writer。旧锁可保留到目标结果明确，释放顺序须与恢复策略一并测试；同文件替换连续持锁。
   - 标准 RPC 没有 shutdown 命令，计划停止只能关闭 stdin。关闭后子进程收不到对话框回答，所以**关闭阶段的交互不受支持**。G2 证实此时子进程不会挂起，而是立即以 0 退出并截断关闭处理，所以退出码 0 不能当作关闭处理已完整执行的证据：stdin 关闭后只要出现过对话框请求，就判定这次停止不完整。
   - 慢的关闭处理会被子进程等待（G2 实测 3.5 秒的处理完整执行），所以正常替换的等待上限单独设定，不沿用 M3 紧急退出的 2 秒 SIGTERM/5 秒 SIGKILL；等待期间用户可停止整个服务。停止不完整或被强制结束时不激活目标，进入 recovery_required 并说明原因；这类扩展存在时，项目切换在网页不可用，需 Ctrl+C 后在终端进行。
4. 更新 writer PID后、打开启动门前再次验证目标文件未被外部修改。sidecar不阻止普通TUI；恢复旧会话也要核对保留基线，不无条件acceptChanges。`runHandoff`改用宿主级完成/故障信号监督当前 generation，不能继续 race 最初的 `childExited`。
   - 关闭窗口（关闭 stdin 到 child 退出）内的追加**无法证明归属**：归属校验依赖存活 child 的 `get_entries`。这与 M3 在 TUI 关闭后直接接受其最后写入是同一类残余风险，文档如实说明，不称为已核对。
   - 默认采用有界接受规则（G2 校验，可收紧）：文件只增不改、已接受前缀哈希不变、每行是合法条目、不含 user/assistant 消息条目、child 退出后文件不再变化。实现已收紧为拒绝任何消息条目、不完整的末行和被替换的文件。满足则接受并记录条数。出现消息条目（说明停止时有回合在进行，例如扩展在空闲复核后自行发起）、结构不合法、或 child 退出后仍有写入时，不激活目标：同文件重建则停服务，跨项目则进入 recovery_required。
5. 只有 get_state、snapshot、锁所有权有效后才发布成功；已落盘会话另核对 header cwd 与目标一致。spawn成功不算切换成功。RPC `get_state` 不含 cwd，未落盘会话没有可读的 cwd 来源：产品运行时以已验证的启动目标为准，不使用旧cwd回退，也不声称已核对子进程实际 cwd；该等价性由 G1 用确定性工具输出证明。
6. 失败后保留 Hub展示恢复状态，但拒绝对话写入；用户显式重试或恢复旧已保存会话。每次都是新的有界操作，不自动循环启动；旧空会话只恢复项目与草稿。没有安全恢复路径时停服务。
7. 发生全局退出/外部写冲突时不进入配置恢复循环。只读请求超时只使本次读取失败；等待认证/扩展对话框不能沿用固定两分钟杀进程策略。用户始终能取消或结束服务。

跨项目切换必须走此流程。凭据应用和需重建运行时的设置优先用 5.2 的进程内应用，只在其被证伪或不适用时回退到此流程；回退时共用同一套代码，避免三套停进程逻辑分叉。认证提交与会话替换是两个结果，不能通过 child启动失败推断凭据未保存。

## 12. 版本、发布与迁移

M3.1是里程碑名，不是npm版本号。建议下一功能版本 **0.3.0**，正式确定须根据最后协议/配置兼容性；不覆盖已发布0.2.0，也不将新增项目/认证能力塞成无迁移说明的修复包。

迁移文档必须解释：项目登记与真实目录的区别；空项目/空会话；新建目录失败的保留策略；账户全局作用域与注销限制；浏览器外观与pi默认；CLI/项目覆盖；跨项目运行时重启及扩展内存/veto限制；关闭终端仍停止服务；工具/tree等剩余缺口；不提供“仅本次信任”及原因；不能经网页打开的凭据类目录；子进程环境来自起始终端；关闭时需要交互的扩展会阻止网页切换项目；关闭窗口追加属有界接受而非归属证明；凭据应用只作用于本宿主；浏览器偏好随端口变化；自定义供应商密钥的保存位置及表单外字段只读；删除会话是废纸篓优先还是永久删除；导出文件位置与内容敏感性；界面改版后的入口位置变化、重做的默认主题、新增的青花瓷主题及装饰开关（装饰只在网页显示，TUI 只有配色）；常用模型范围、资源安装、MCP 管理仍需在终端完成。

发布门槛：G1–G5决策落档、设计规范评审通过 → 承诺功能与验收全部通过 → 新代码真实模型/支持认证路径试用 → 冻结源码及tarball并校验 → 精确候选安装 → 维护者执行npm发布 → 公共registry安装和日常pi插件更新验证 → 源码/文档同步GitHub → 明确标记M3.1完成。仅有计划、spike或本地pack都不能提前完成里程碑。本轮不发布、不改日常插件。

应更新 README、docs/design.md、docs/project.json、tests/README.md，并新增M3.1状态/验收记录；M3完成证据保留，不回写成“原M3未完成”。

## 13. 与 M4 的关系及评审重点

M4原方向继续保留：上游接口兼容、长期稳定性、平台覆盖、压力/重连验证，以及在上游公开能力成熟后评估工具/tree等更深整合。M3.1先补齐独立日常工作流，不恢复已被否决的后台常驻方案，也不提前承诺未验证的上游实验client。

本计划已给出默认选择；开工前重点审阅四项产品取舍：跨项目采用受控child替换及其扩展veto限制；账户沿用agentDir全局作用域与M2 owner边界；项目设置首期只读、全局allowlist可写；常用模型范围、资源安装、MCP 管理、工具/tree继续明确暂缓。修订后新增的五项默认选择同样需要审阅：首版不提供“仅本次信任”；认证交互不占用会话，只有应用需空闲；凭据与设置应用优先进程内原生替换；凭据类目录不能经网页打开为项目；打开已有项目默认恢复最后已保存会话。按对齐标准新增的三项也需审阅：自定义供应商密钥的保存位置；删除会话采用废纸篓优先；青花瓷主题只提供浅色一套。界面风格的方向已确认，纹样装饰的加载机制与青花瓷主题已纳入本期，见第 7 节。技术能否按这些取舍可靠落地由G1–G5验证，不能用“计划已详细”代替实现证据。
